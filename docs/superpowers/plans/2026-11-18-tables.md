# Table Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `dining_tables` with a stored status. `TableStatusService` is the only writer of status: it validates transitions and logs every change. Owner screens create, edit and deactivate tables. The cashier floor shows large touch cards with a color and text status, a status filter, and manual Reserved/Cleaning/Available changes. The API is `GET /api/v1/tables` and `PATCH /api/v1/tables/{id}/status`. Ten sample tables are seeded in local only.

**Spec:** `docs/YANGS_SPEC.md` §4A; owner's Step 8 brief; `docs/ARCHITECTURE.md` §3.1 (revised by this plan); `design-system/YANGS/MASTER.md`.

## Global Constraints
- Statuses: `available`, `occupied`, `awaiting_payment`, `reserved`, `cleaning`. Status is never shown by color alone.
- Every status change goes through `TableStatusService` in a transaction, with the row locked and a `table.status_changed` log.
- Permissions:
  - `tables.view` (floor, list API).
  - `tables.update-status` (new; manual status changes; Cashier default).
  - `tables.manage` (create, edit, deactivate).
- Deactivated tables are hidden from the floor and from the list API (managers can include them).
- Sample tables are seeded only when `app()->environment('local')`.

## Rulings
1. **Status is stored, with one writer.** The brief stores all five statuses; ARCHITECTURE.md §3.1 derived Occupied and Awaiting Payment from sessions.
   - Manual changes only move between Available, Reserved and Cleaning.
   - Occupied and Awaiting Payment are system transitions that the session service (Step 11) calls in its own transaction.
   - *Cost if wrong:* status can drift from sessions only if someone bypasses the service.
2. **Allowed transitions:**
   - **Manual:** {available, reserved, cleaning} → each other.
   - **System:**
     - available or reserved → occupied;
     - occupied ⇄ awaiting_payment;
     - occupied or awaiting_payment → available or cleaning.
   - **Same status:** a no-op, with no log.
3. **New permission `tables.update-status`.**
   - The seeder now grants newly added Cashier-default permissions to an existing Cashier role once, when the permission is first created.
   - Owner edits to existing permissions are still never overwritten.
4. **A table cannot be deactivated while occupied or awaiting payment.** An inactive table refuses status changes.
5. **The cashier floor replaces the cashier dashboard.** `/dashboard` redirects cashiers to `/floor`.
6. **Out of scope:** table kind (counter/takeout) and an owner CRUD API. Neither was asked for, and both can be added later.

## Review Focus
- Two tablets change the same table at once: the row lock serializes them, and the second change is validated against the new status.
- Someone tries to mark an occupied table Available: rejected with a message that says why.
- Labels like `t1` and `T1` must not both exist.
- A deactivated table must not appear on the floor, in the API list, or in the status filter counts.
- Narrow tablet (768 portrait): no sideways scroll, and every card is at least 48px tall.

### Task 1: Schema, enum, permission, seeders
- **Migration `dining_tables`:**
  - `label` unique, case-insensitive;
  - `capacity` nullable, smallint > 0;
  - `status` with a check constraint, default `available`;
  - `is_active` default true;
  - `sort_order`, timestamps.
- **Enum `TableStatus`:** `label()`, `isManual()`, `canMoveTo(self $to, bool $system): bool`.
- **Permission:** `Permission::TablesUpdateStatus`, added to Cashier defaults. Seeder change per ruling 3.
- **Seeders:** `SampleTableSeeder` (T1–T10), called from `DatabaseSeeder` in local only.
- **Tests:** seeder grants the new default once; sample tables are idempotent; nothing is seeded outside local.

### Task 2: TableStatusService and table service
- `TableStatusService::change(DiningTable $table, TableStatus $to, bool $system = false, ?string $reason = null): DiningTable`.
- `DiningTableService`: `create`, `update`, `setActive`.
- **Tests:**
  - allowed manual and system paths;
  - manual Occupied rejected, manual from Occupied rejected, invalid system jumps rejected;
  - same status is a no-op;
  - inactive table refused;
  - deactivating an occupied table refused;
  - logs written.

### Task 3: Web
- **Owner:** `/tables` list, plus create and edit pages and an active switch (`tables.manage`).
- **Floor:** `/floor` in the POS layout (`tables.view`): status filter chips with counts, and table cards that open a dialog with the allowed manual changes (`PATCH /tables/{table}/status`, `tables.update-status`).
- Navigation entries. Cashier dashboard redirects to the floor.
- **Tests:** management, floor visibility, filter, status change, invalid change message, permissions.

### Task 4: API
- `GET /api/v1/tables` (`?status=`; `?include_inactive=1` for managers) and `PATCH /api/v1/tables/{table}/status` returning `TableResource`.
- **Tests:** list, filter, change, 422 on invalid, 403, 401.

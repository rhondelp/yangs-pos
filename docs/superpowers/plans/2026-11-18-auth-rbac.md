# Authentication and RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Username login (web via Breeze Blade, API via Sanctum tokens), no public registration, deactivation that blocks access, database-driven roles with a permission matrix editor, owner user management, and audit entries for every account and permission change.

**Architecture:** Breeze provides the web auth scaffold; spatie/laravel-permission stores roles and permissions; permission names live in one PHP enum that the seeder syncs to the database. Business rules (last owner, self-deactivation, token revocation, audit) live in `UserService` and `RolePermissionService`, shared by web and API controllers. Every authenticated route carries a `can:` middleware unless it is on a short allow list, and a test enforces that.

**Tech Stack:** Laravel 13, laravel/breeze 2.4 (Blade, PHPUnit), spatie/laravel-permission 8.5, laravel/sanctum, PostgreSQL 18, Tailwind 4, Alpine.js.

**Spec:** `docs/YANGS_SPEC.md` sections 3, 9, 13; `docs/ARCHITECTURE.md` 3.12–3.14; owner's Step 4 brief (2026-11-18); `CLAUDE.md`.

## Global Constraints

- Packages: only `laravel/breeze`, `spatie/laravel-permission`, `laravel/sanctum`.
- No public registration. No hard deletes of users (deactivate only).
- Owner account from env (`OWNER_NAME`, `OWNER_USERNAME`, `OWNER_EMAIL`, `OWNER_PASSWORD`); no hardcoded password; seeding fails if the password is empty.
- Seeded roles: Owner (all permissions), Cashier (POS only), Supervisor, Bartender, Staff, Inventory Manager (empty).
- Permission names `module.action`, kebab-case actions, including the owner's examples: `pos.create-order`, `orders.cancel-item`, `payments.record`, `payments.refund`, `products.manage`, `inventory.manage`, `finance.view`, `employees.manage`, `payroll.manage`, `reports.view`, `users.manage`, `logs.view`, `settings.manage`.
- Login rate limit: 5 attempts per minute per username + IP, web and API.
- Every account/role change and every login, logout and failed login writes an activity log row.
- Business logic in services, validation in Form Requests, authorization via policies/permissions, API output via Resources.

## Rulings (deviations from the brief or the earlier design)

1. Login field is `username` (ARCHITECTURE.md 3.13: bar staff may have no email); `email` is optional.
2. Keep Tailwind 4: Breeze's Blade stub installs Tailwind 3 + PostCSS; restore `vite.config.js` and `app.css` to Tailwind 4 with `@plugin '@tailwindcss/forms'`, delete `tailwind.config.js` and `postcss.config.js`. Visual polish waits for the design system step.
3. Remove Breeze's registration, password reset, email verification, password confirmation, and profile name/email edit and account delete (no mail configured; no hard deletes). Keep "change my password".
4. Permission catalogue follows the owner's kebab-case examples; ARCHITECTURE.md 3.12 is updated to match. Supervisor is seeded empty (brief overrides the doc).
5. A minimal `activity_logs` table and `ActivityLogger` are built now, because the audit rule applies to this step's actions.
6. Finance, payroll and settings routes do not exist yet. A route-guard test asserts that every authenticated web and API route has a `can:` middleware unless allow-listed, so later modules cannot ship unguarded. The cashier-blocked test covers the owner routes that exist now (users, roles) on web and API.
7. Users can hold one role each (UI picks one); spatie supports more, unused.

## Review Focus

- Owner locks themselves out: deactivating self, demoting or deactivating the last active Owner, or editing the Owner role's permissions must be rejected.
- Deactivated user with a live session or token: next request must be rejected (web logs out; API 401) and their tokens deleted.
- Stale permission cache: after a matrix change, the affected user's next request reflects it.
- Username case: `Owner` and `owner` must be the same account (stored lowercase, unique).
- Secrets in logs: passwords and tokens never appear in `activity_logs` values.
